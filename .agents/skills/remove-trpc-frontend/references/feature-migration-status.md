# Feature Migration Status Reference

This is the working reference for removing frontend TRPC code after REST parity exists. It complements `.agents/skills/rest-migration-plan/SKILL.md`, which contains fuller migration detail and E2E scenarios.

Treat this file as a snapshot. Before removing code, always verify with `rg` because service imports and tests may have changed since this reference was last edited.

## Status Values

| Status            | Meaning                                                                                                                         | Removal guidance                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `complete`        | Feature is already REST-backed and no known direct frontend `lambdaClient` usage remains outside legacy service fallback/tests. | Candidate for removing resolver/TRPC fallback after targeted tests pass.                 |
| `mostly-complete` | REST path exists and most consumers use it, but a known compat path, direct call, or test-only TRPC assumption remains.         | Remove only after verifying the remaining dependency is unnecessary or migrated.         |
| `resolved-in-use` | `.rest.ts` and `.resolved.ts` exist and stores/features are expected to use the resolver.                                       | Do not delete resolver until every operation is REST-backed and imports can be promoted. |
| `partial`         | REST services exist but known direct frontend `lambdaClient` usage remains.                                                     | Migrate direct calls first; do not remove shared resolver.                               |
| `blocked`         | REST parity or transport semantics are unclear.                                                                                 | Use `trpc-to-rest` or `hono-python-rest-parity` before removal.                          |
| `test-gap`        | Code appears migrated but existing test coverage is missing or still asserts TRPC behavior.                                     | Update/run targeted tests before deleting fallback code.                                 |
| `removed`         | TRPC frontend service/resolver fallback has been removed for the feature.                                                       | Keep only if validated and documented with tests run.                                    |

## Update Rules

When a feature cleanup is completed:

1. Change only that feature row.
2. Set status to `removed` only after targeted frontend tests pass and no relevant `lambdaClient.<namespace>` usage remains outside unrelated tests or backend code.
3. Add a concise note with the tests run, for example: `Removed fallback in 2026-05; ran src/services/__tests__/brief.test.ts`.
4. If removal is blocked, keep the status as `partial`, `blocked`, or `test-gap` and record the exact remaining file or missing endpoint.

## Quick Verification Commands

Replace placeholders before running:

```bash
rg -n "lambdaClient\\.<namespace>|<domain>\\.resolved|from '@/services/<domain>" src test packages apps --glob '*.{ts,tsx}'
rg -n "restClient\\.(get|post|put|patch|delete)" src/services/ src/services/ '*.{ts,tsx}' < domain > * < domain > --glob
rg -n "@router\\.(get|post|put|patch|delete)\\(" python-backend/app/routers/ < router > .py
```
